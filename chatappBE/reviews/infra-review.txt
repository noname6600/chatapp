──────────────────────────────────────────────────────────────────────────────
[STRENGTH] Health Check Strategy Is Production-Quality
──────────────────────────────────────────────────────────────────────────────
File: chatappBE/docker-compose.yml

Health check approach:
  - PostgreSQL: pg_isready (checks if Postgres can accept connections)
  - Redis: redis-cli ping (checks Redis responsiveness)
  - Kafka: kafka-broker-api-versions (checks if broker API is available — better than just TCP check)
  - Zookeeper: echo ruok | nc localhost 2181 (checks Zookeeper four-letter word protocol)
  - Microservices: wget to /actuator/health (verifies Spring Boot application readiness)
  - Gateway: wget to /actuator/health/readiness (verifies downstream readiness)
  - Frontend: curl to / (verifies Nginx/frontend serving)

Using actuator health (not just TCP port check) means services are only marked
healthy when Spring Boot has fully initialized and all health indicators pass.

start_period: 60s for microservices accounts for JVM warmup + Hibernate DDL.
This prevents premature unhealthy marking during JVM startup.

Assessment: This is better than most production docker-compose files.

──────────────────────────────────────────────────────────────────────────────
[CRITICAL] realtime-edge-service Missing From docker-compose.yml
──────────────────────────────────────────────────────────────────────────────
Severity: CRITICAL
File: chatappBE/docker-compose.yml

realtime-edge-service (port 8090) is a complete, fully implemented service
(has Dockerfile, application.yaml, settings.gradle entry, full implementation)
but has NO service entry in docker-compose.yml.

Impact:
  1. docker compose up does NOT start realtime-edge-service
  2. WebSocket connections must use the legacy per-service paths
  3. The realtime-edge architecture is unreachable in any docker-compose deployment
  4. Any production deployment using docker-compose has split WebSocket behavior:
     - /ws/chat → chat-service's legacy handler (not realtime-edge)
     - /ws/presence → presence-service's legacy handler (not realtime-edge)
     - etc.

This is a deployment artifact gap that makes the new architecture inaccessible
without manual service startup.

Recommended fix direction:
  Add realtime-edge-service to docker-compose.yml:
    realtime-edge:
      build:
        context: .
        dockerfile: realtime-edge-service/Dockerfile
      container_name: chatapp-realtime-edge
      depends_on:
        redis:
          condition: service_healthy
        auth-service:
          condition: service_healthy
        chat-service:
          condition: service_healthy
        presence-service:
          condition: service_healthy
        friendship-service:
          condition: service_healthy
        notification-service:
          condition: service_healthy
      environment:
        PORT: 8090
        SPRING_DATA_REDIS_HOST: redis
        SPRING_DATA_REDIS_PORT: 6379
        SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI: http://auth-service:8081/.well-known/jwks.json
        SERVICES_CHAT_URL: http://chat-service:8083
        SERVICES_PRESENCE_URL: http://presence-service:8084
        SERVICES_FRIENDSHIP_URL: http://friendship-service:8085
        SERVICES_NOTIFICATION_URL: http://notification-service:8086
        CORS_ALLOWED_ORIGINS: ${CORS_ALLOWED_ORIGINS:-http://localhost:5173}
        REALTIME_SESSION_REGISTRY_MODE: distributed
      networks:
        - chatapp-net
      restart: unless-stopped
      healthcheck:
        test: ["CMD-SHELL", "wget -q -O /dev/null http://localhost:8090/actuator/health || exit 1"]
        interval: 30s
        timeout: 10s
        retries: 3
        start_period: 60s

  Also update gateway-service depends_on to include realtime-edge.
  Update nginx to route /ws/** to realtime-edge:8090.

──────────────────────────────────────────────────────────────────────────────
[HIGH] Single Node Infrastructure — No High Availability for Any Component
──────────────────────────────────────────────────────────────────────────────
Severity: HIGH
File: chatappBE/docker-compose.yml

Every component runs as a single container:
  - 1 PostgreSQL → SPOF for all 6 services
  - 1 Redis → SPOF for rate limiting, cache, presence, pub/sub
  - 1 Kafka broker → SPOF for all async events
  - 1 Zookeeper → SPOF for Kafka cluster management
  - 1 Nginx → SPOF for external traffic ingress

Docker Compose is a single-node orchestrator. It cannot restart containers on a
different physical host if the host fails.

Assessment: Acceptable for development and staging. Not acceptable for production
  serving real users without at minimum a manual failover procedure.

Recommended fix direction:
  Migrate to Kubernetes or Docker Swarm for production:
  - Kubernetes: Deployment + PodDisruptionBudget for services
  - Managed databases: RDS (PostgreSQL), ElastiCache (Redis)
  - Managed Kafka: Confluent Cloud, Amazon MSK, or self-managed multi-broker

──────────────────────────────────────────────────────────────────────────────
[HIGH] Gateway depends_on All 7 Services — Deployment Paralysis Risk
──────────────────────────────────────────────────────────────────────────────
Severity: HIGH
File: chatappBE/docker-compose.yml (gateway-service depends_on block)

gateway-service depends_on:
  redis, auth-service, user-service, chat-service, presence-service,
  friendship-service, notification-service, upload-service
  (all condition: service_healthy)

With DownstreamReadinessIndicator also requiring all services UP for
gateway readiness probe:
  - If notification-service fails to start (DB migration issue, config error):
    → gateway readiness fails
    → nginx dependency on gateway healthy fails
    → nginx doesn't start (or restarts)
    → ALL user traffic blocked

This creates a deployment scenario where a single non-critical service can
prevent the entire platform from serving requests.

Recommended fix direction:
  Change depends_on conditions for non-critical services to service_started
  (not service_healthy). This allows gateway to start even if secondary
  services are unhealthy. The per-route 503 response handles the degradation.
  Critical: auth-service, user-service, chat-service (keep service_healthy)
  Optional: notification-service, upload-service (change to service_started)

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] Certbot Entrypoint Override Suppresses Default Renewal Logic
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml (certbot service)

certbot service:
  entrypoint: ["certbot"]
  command: ["--version"]
  restart: "no"

This certbot container just runs `certbot --version` and exits. It's a one-time
setup container for INITIAL certificate issuance (presumably run manually with
different command arguments).

certbot-renew service runs the renewal loop (every 12 hours). This is correct.

However, the INITIAL certificate issuance process is not documented in docker-compose.
A new deployment would need manual steps to issue the certificate before nginx can
serve HTTPS traffic. If nginx starts before certificates exist, it may fail or
serve HTTP only.

Recommended fix direction:
  Document the certificate issuance process in README:
  1. First run: certbot container with certonly --standalone (before nginx starts)
  2. Or: Start with HTTP-only nginx, issue cert via webroot challenge, then switch to HTTPS
  Add a staging.docker-compose.yml for local development without HTTPS.

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] No Docker Secrets Usage — All Sensitive Config via Environment Variables
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml

All sensitive configuration (DB passwords, API keys, JWT secrets) is passed
via environment variables. Docker Secrets (Swarm mode) or Kubernetes Secrets
mounted as files would be more secure:
  - Environment vars visible in docker inspect
  - File-mounted secrets not visible in docker inspect
  - File-mounted secrets can be rotated without container restart (if using Vault)

Recommended fix direction:
  For Docker Swarm: use secrets: field in docker-compose.yml with external secrets.
  For Kubernetes: use Secret resources mounted as environment or files.
  For local dev: environment variables are acceptable.

──────────────────────────────────────────────────────────────────────────────
[HIGH] Nginx Config File Not Reviewed (Not Readable From Available Data)
──────────────────────────────────────────────────────────────────────────────
Severity: HIGH
File: chatappBE/nginx/nginx.conf

The nginx.conf content was not read in the code analysis. Critical security
and performance configurations that need verification:

  1. WebSocket upgrade headers: Upgrade + Connection headers must be proxied
  2. Security headers: X-Frame-Options, X-XSS-Protection, HSTS, CSP
  3. Rate limiting at nginx level (in addition to gateway rate limiting)
  4. Buffer sizing for large file uploads (proxy_buffer_size)
  5. Timeout configuration for long-running WebSocket connections
     (proxy_read_timeout must be >> WebSocket idle timeout)
  6. gzip compression enabled?
  7. Static asset caching headers for frontend

Recommended fix direction:
  Review nginx.conf for:
  - Add HTTP security headers (HSTS, X-Frame-Options, X-Content-Type-Options)
  - Ensure proxy_read_timeout is at least 3600s for WebSocket connections
  - Add `proxy_set_header Upgrade $http_upgrade` for WebSocket routes
  - Add `proxy_set_header Connection "upgrade"` for WebSocket routes

SECTION 4 — OBSERVABILITY READINESS
================================================================================

──────────────────────────────────────────────────────────────────────────────
[HIGH] No Metrics Exporter Configured — Flying Blind in Production
──────────────────────────────────────────────────────────────────────────────
Severity: HIGH
Files: All service application.yaml files
  management.endpoints.web.exposure.include: health,info

Spring Boot Actuator exposes health and info. Metrics endpoint is NOT exposed.
No micrometer-registry-prometheus dependency visible in build files.
No Prometheus scrape targets. No Grafana dashboards.

In production this means:
  - No visibility into JVM heap usage (cannot detect memory leaks)
  - No visibility into HTTP request rates and latency percentiles
  - No visibility into DB connection pool utilization (Hikari metrics)
  - No visibility into Kafka consumer lag (cannot detect processing backlogs)
  - No visibility into circuit breaker state transitions
  - No visibility into Redis memory usage

Operating a production system without metrics is dangerous. Issues are discovered
only when users complain or the service crashes.

Recommended fix direction:
  1. Add to each service build.gradle:
       runtimeOnly 'io.micrometer:micrometer-registry-prometheus'
  2. Expose metrics endpoint:
       management.endpoints.web.exposure.include: health,info,metrics,prometheus
  3. Deploy Prometheus + Grafana in docker-compose
  4. Create dashboards for: request rate, error rate, latency P99, JVM heap,
     DB pool, Kafka consumer lag, circuit breaker state

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] No Centralized Log Aggregation
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml (no logging driver configuration)

All containers write logs to Docker's default json-file logging driver.
Logs are accessible via `docker logs container-name` but:
  - No centralized log search
  - Log rotation not configured (json-file grows indefinitely)
  - No structured log parsing (JSON logs from Spring are not indexed)
  - Correlating logs across services requires manual examination of 9 containers

Recommended fix direction:
  Option A: Add ELK stack (Elasticsearch + Logstash + Kibana) to docker-compose
  Option B: Add Loki + Grafana (lighter weight than ELK)
  Option C: Configure Docker logging driver to forward to external logging service
    (Datadog, CloudWatch, Splunk)

  Immediate: Add log rotation to docker-compose:
    logging:
      driver: "json-file"
      options:
        max-size: "100m"
        max-file: "5"

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] Distributed Tracing Not Implemented
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: common-web/.../filter/TraceIdFilter.java (manual traceId via MDC)

The system uses manual X-Trace-Id header propagation. This provides:
  - Per-request traceId in logs
  - Correlation within a single service

Does NOT provide:
  - End-to-end trace visualization across services
  - Span timing (how long each service took in a cross-service request)
  - Automatic HTTP/Kafka/DB span tracking
  - Integration with Jaeger/Zipkin/Tempo for trace search

Without distributed tracing, debugging a production performance issue that
spans auth-service → gateway → chat-service → friendship-service requires
manually correlating logs from 4 containers by timestamp and traceId.

Recommended fix direction:
  Add Spring Boot OpenTelemetry auto-instrumentation:
    implementation 'io.micrometer:micrometer-tracing-bridge-otel'
    implementation 'io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter'
  This auto-instruments: HTTP, Kafka, JDBC, Redis with zero code changes.
  Deploy Jaeger (or Tempo) for trace storage and UI.

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] All Services Built From Same Docker Context (.) — Slow Builds
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml (all services: context: .)

All Dockerfile builds use the entire chatappBE directory as build context.
This means:
  - Every build copies the ENTIRE codebase to Docker daemon
  - If chatappBE is 200MB (compiled sources, caches): 200MB × 9 services = 1.8GB transfer
  - Build times: Gradle multi-module build runs for EVERY service rebuild
  - Cache invalidation: changing auth-service source invalidates ALL service images

Recommended fix direction:
  1. Use .dockerignore to exclude unnecessary files:
     .gradle, build/, .git, *.md, *.txt, node_modules
  2. Consider using Gradle --build-cache and --parallel for faster builds
  3. Use multi-stage Dockerfile with Gradle cache mount:
     RUN --mount=type=cache,target=/root/.gradle ./gradlew :service:bootJar
  4. In CI: build only the services whose source files changed (path filtering)

SECTION 6 — DOCKER QUALITY REVIEW
================================================================================

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] No Resource Limits on Containers
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml (no deploy.resources sections)

No CPU or memory limits are set on any container. In a single-host deployment:
  - A runaway Java process (e.g., memory leak in chat-service) can consume all host RAM
  - Host OOM killer may kill unrelated containers (e.g., PostgreSQL)
  - No container can be allocated more than host resources → resource contention

Recommended fix direction:
  Add resource limits for production:
  deploy:
    resources:
      limits:
        cpus: '2'
        memory: 1G
      reservations:
        memory: 512M

  Tune per service based on observed usage.

──────────────────────────────────────────────────────────────────────────────
[MEDIUM] No Explicit Healthcheck on Kafka Consumer Readiness
──────────────────────────────────────────────────────────────────────────────
Severity: MEDIUM
File: chatappBE/docker-compose.yml (kafka healthcheck)

Kafka healthcheck uses: kafka-broker-api-versions --bootstrap-server localhost:9092
This checks broker API availability. It does NOT verify:
  - Whether specific topics exist
  - Whether consumer groups are properly registered
  - Whether the Zookeeper/KRaft metadata is consistent

Services that depend on Kafka (notification-service, user-service) wait for
kafka: condition: service_healthy. If Kafka reports healthy but topics are not
yet created (auto-creation takes a few seconds), consumer startup may fail
with "Unknown topic or partition" error.

Recommended fix direction:
  Add a startup check in each Kafka consumer service that retries consumer
  initialization until the target topic is available. Spring Kafka's
  @RetryableTopic or a @PostConstruct with retry handles this.
