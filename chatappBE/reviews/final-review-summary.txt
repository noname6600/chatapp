════════════════════════════════════════════════════════════════════════════════
FUTURE RISKS (Non-Immediate but Worth Tracking)
════════════════════════════════════════════════════════════════════════════════

  FR-1: Schema lock-in — ddl-auto: update will fail catastrophically on first
         non-additive schema change with real production data.
         (Addressed by BLOCKER-1 fix)

  FR-2: Event format lock-in — no versioning means schema evolution requires
         coordinated multi-service deployment or silent backward compatibility.

  FR-3: Redis memory pressure — all services share one Redis. At 100K users,
         presence state alone = 300K+ keys. No eviction policy configured.
         Action: Set maxmemory + maxmemory-policy: allkeys-lru on Redis.

  FR-4: Notification volume explosion — 1 message to 1K-member group = 1K notifications.
         No batching, no rate limiting per user. At large group sizes, notification
         DB write volume becomes unsustainable.
         Action: Batch notifications (1 per room/hour if not mentioned).

  FR-5: Kafka consumer lag silent failures — no monitoring for consumer lag.
         A slow notification-service will silently fall behind without alerting.
         Action: Monitor kafka_consumer_lag metric in Prometheus/Grafana.

  FR-6: Google OAuth dependency without fallback — Google outage = OAuth login unavailable.
         Action: Ensure local auth is always available as fallback.

  FR-7: Privacy/GDPR gap — no user data deletion mechanism visible.
         A user's messages, profile, notifications, friendship records span 6 databases.
         No DELETE endpoint for user data exists in the current codebase.
         Action: Implement cross-service user deletion flow (Kafka event: ACCOUNT_DELETED).

FINAL VERDICT
════════════════════════════════════════════════════════════════════════════════

OVERALL ASSESSMENT: B (Excellent Foundation, Significant Operational Gaps)

This is a technically competent, well-structured codebase built by an engineer
who understands distributed systems concepts deeply. The architecture decisions
are principled: JWT key rotation, token theft detection, pipeline pattern,
event-driven design, and domain separation all show advanced thinking.

However, the gap between the code's technical quality and production operational
readiness is significant. The blockers (no migrations, missing realtime-edge
in compose) and criticals (credentials, sequence bottleneck, single Kafka broker)
represent real risks that would cause user-facing failures within hours of
launch at meaningful traffic.

The path to production is clear and achievable. Phase 1 can be completed in 2-3
weeks by a single developer. After Phase 1 and Phase 2, this system is ready
for production operation with real users at small-to-medium scale (up to ~50K DAU).
Phase 3 unlocks large-scale operation (100K-500K DAU).

The codebase is a strong foundation. The investment to production-harden it is
proportionate to what has already been built. Execute the roadmap, and this
becomes a system worth being proud of in production.
