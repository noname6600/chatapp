## 1. Summary
- Today the realtime architecture is still service-local, not edge-centralized. `gateway-service` proxies four separate WebSocket routes, and `chat-service`, `presence-service`, `friendship-service`, and `notification-service` each still own their own WebSocket endpoint and/or local delivery stack (`gateway-service/src/main/resources/application.yaml:85-151`, `chat-service/src/main/java/com/example/chat/config/WebSocketConfig.java:20-29`, `presence-service/src/main/java/com/example/presence/configuration/WebSocketConfig.java:19-30`, `friendship-service/src/main/java/com/example/friendship/configuration/FriendshipWebSocketConfig.java:21-27`, `notification-service/src/main/java/com/example/notification/configuration/WebSocketConfig.java:21-28`).
- Realtime ownership is fragmented. The shared modules describe future edge-oriented publication contracts, but the current implementations still deliver locally through service-owned WebSocket session registries, Redis listeners, and direct broadcasters (`chat-service/src/main/java/com/example/chat/realtime/publisher/ChatRealtimeEventPublisher.java:5-11`, `friendship-service/src/main/java/com/example/friendship/realtime/publisher/FriendshipRealtimeEventPublisher.java:5-10`, `notification-service/src/main/java/com/example/notification/realtime/publisher/NotificationRealtimeEventPublisher.java:5-10`, `presence-service/src/main/java/com/example/presence/realtime/publisher/PresenceRealtimeEventPublisher.java:5-9`).
- The codebase is not ready for a single `realtime-edge-service`.
- Main-source compilation does succeed for the in-scope backend modules via `.\gradlew :chat-service:compileJava :friendship-service:compileJava :notification-service:compileJava :presence-service:compileJava :gateway-service:compileJava` from `chatappBE` on 2026-05-12.
- Runtime verification is incomplete. In-scope test suites for `chat-service` and `notification-service` do not currently compile because they still reference removed contract classes and package names (`chat-service/src/test/java/com/example/chat/realtime/contract/RealtimeContractBaselineTest.java:6`, `chat-service/src/test/java/com/example/chat/realtime/contract/RealtimeMessagingAlignmentTest.java:4-7`, `notification-service/src/test/java/com/example/notification/contract/NotificationRealtimeContractBaselineTest.java:3`, `notification-service/src/test/java/com/example/notification/kafka/FriendRequestEventConsumerTest.java:3-4`, `notification-service/src/test/java/com/example/notification/application/NotificationKafkaEventApplicationServiceTest.java:7`).

## 3. Findings
### High
- WebSocket ownership is still split across four domain services, with gateway proxy routes preserving that split instead of collapsing it. The current runtime owners are `chat-service`, `presence-service`, `friendship-service`, and `notification-service`, each with its own endpoint, handler, session registry, and broadcaster set (`gateway-service/src/main/resources/application.yaml:85-151`, `chat-service/src/main/java/com/example/chat/config/WebSocketConfig.java:20-29`, `presence-service/src/main/java/com/example/presence/configuration/WebSocketConfig.java:19-30`, `friendship-service/src/main/java/com/example/friendship/configuration/FriendshipWebSocketConfig.java:21-27`, `notification-service/src/main/java/com/example/notification/configuration/WebSocketConfig.java:21-28`).
- `chat-service` still owns both realtime ingress and local client delivery for several core flows. `ChatWebSocketHandler` accepts business commands directly over WebSocket (`SEND`, `EDIT`, `DELETE`, `REACTION`, `JOIN`, `LEAVE`) (`chat-service/src/main/java/com/example/chat/realtime/websocket/handler/ChatWebSocketHandler.java:96-216`), while room membership and moderation events still route to direct local fanout through `ChatRealtimeAdapter` instead of an off-box contract (`chat-service/src/main/java/com/example/chat/realtime/infrastructure/ChatRealtimeAdapter.java:63-145`, `chat-service/src/main/java/com/example/chat/modules/room/service/impl/RoomService.java:146-157`, `195-204`, `270-279`, `303-312`, `chat-service/src/main/java/com/example/chat/modules/room/service/impl/RoomModerationApplicationService.java:49-56`). Consolidating sockets into an edge service would break these flows unless they are first externalized.
- Friendship request events are contract-inconsistent today. The shared catalog says `friend.request.sent`, `friend.request.accepted`, `friend.request.declined`, and `friend.request.cancelled` must carry `FriendRequestPayload` (`common/common-events/src/main/java/com/example/common/event/SharedEventCatalog.java:110-117`), and `notification-service` consumes those topics as `EventEnvelope<FriendRequestPayload>` (`notification-service/src/main/java/com/example/notification/kafka/FriendRequestEventConsumer.java:19-36`). But `friendship-service` currently publishes `FriendshipPayload` for all friendship event types, including request lifecycle events (`friendship-service/src/main/java/com/example/friendship/kafka/FriendshipEventProducer.java:30-55`, `common/common-events/src/main/java/com/example/common/integration/friendship/FriendRequestPayload.java:12-47`, `common/common-events/src/main/java/com/example/common/integration/friendship/FriendshipPayload.java:10-31`). This makes the friendship realtime path at least partial and likely broken.
- `presence-service` is not a pure presence domain service; it is also the current connection and session owner. Connection establishment drives `presenceService.online`, `heartbeat`, and immediate snapshot delivery, while disconnect drives `offline` and room re-notification (`presence-service/src/main/java/com/example/presence/websocket/handler/PresenceWebSocketHandler.java:40-63`, `131-183`). `PresenceSessionRegistry` also owns user/session/room membership in memory (`presence-service/src/main/java/com/example/presence/websocket/session/PresenceSessionRegistry.java:17-185`). Moving connections to edge would require explicit migration of those lifecycle responsibilities.
- Chat pin/unpin is not on a stable shared contract. `SharedEventCatalog` registers `chat.message.pinned` and `chat.message.unpinned` to shared `MessagePinPayload` (`common/common-events/src/main/java/com/example/common/event/SharedEventCatalog.java:103-107`), but `chat-service` re-registers those same event types to local `RoomMessagePinEventPayload` in `ChatRedisEventConfig` (`chat-service/src/main/java/com/example/chat/config/ChatRedisEventConfig.java:38-46`). `DefaultEventPayloadRegistry` explicitly throws on conflicting registrations (`common/common-events/src/main/java/com/example/common/event/DefaultEventPayloadRegistry.java:16-24`). Even before edge extraction, that means the active chat pin/unpin contract is brittle.

### Medium
- `notification-service` has two active-looking `NotificationRealtimePort` implementations with no `@Primary` or `@Qualifier`: `NotificationWebSocketPublisher` and `NotificationRedisRealtimeAdapter` (`notification-service/src/main/java/com/example/notification/websocket/NotificationWebSocketPublisher.java:18-87`, `notification-service/src/main/java/com/example/notification/realtime/infrastructure/NotificationRedisRealtimeAdapter.java:16-39`). `NotificationPushService` injects the interface directly (`notification-service/src/main/java/com/example/notification/service/impl/NotificationPushService.java:17-47`), so the actual runtime adapter choice is not proven from code inspection alone.
- The shared websocket stack exists, but it is not the actual runtime standard for the in-scope services. `common-websocket` auto-configures `SpringRealtimeLifecycleAdapter`, `SpringRealtimeTextWebSocketHandler`, shared session/subscription registries, and `DefaultRealtimeBroadcaster` (`common/common-websocket/src/main/java/com/example/common/websocket/config/RealtimeWebSocketAutoConfiguration.java:32-156`), yet no in-scope service uses `SpringRealtimeTextWebSocketHandler` in main code. Instead, each service keeps its own custom handler and registry.
- Chat message publication is not truly "durable-first" even where the flow policy says it should be. `PublishMessageEventStep` deliberately sends events asynchronously and logs failures as best-effort (`chat-service/src/main/java/com/example/chat/modules/message/application/pipeline/send/steps/PublishMessageEventStep.java:57-69`), and `ChatMessageEventPublisherAdapter` publishes Redis before Kafka for message-sent and reaction-updated (`chat-service/src/main/java/com/example/chat/modules/message/infrastructure/redis/ChatMessageEventPublisherAdapter.java:70-72`, `86-98`). `ChatRealtimeAdapter` also contains TODO markers where flow-based Kafka routing is still not implemented (`chat-service/src/main/java/com/example/chat/realtime/infrastructure/ChatRealtimeAdapter.java:63-96`).
- Friendship realtime delivery is only partially implemented in-code. `FriendshipWebSocketPublisher` contains a comment that `FRIEND_REQUEST_SENT` is "Handled by FriendRequestEventConsumer" (`friendship-service/src/main/java/com/example/friendship/websocket/FriendshipWebSocketPublisher.java:195-203`), but no such consumer exists in `friendship-service`, and `FriendshipKafkaEventApplicationService` is present but unused (`friendship-service/src/main/java/com/example/friendship/application/FriendshipKafkaEventApplicationService.java:16-112`).
- Runtime verification is blocked by stale in-scope tests. `chat-service` tests still import removed realtime contract APIs (`chat-service/src/test/java/com/example/chat/realtime/contract/RealtimeContractBaselineTest.java:6`, `chat-service/src/test/java/com/example/chat/realtime/contract/RealtimeMessagingAlignmentTest.java:4-7`, `chat-service/src/test/java/com/example/chat/realtime/contract/RealtimeContractValidatorTest.java:3-5`). `notification-service` tests still import removed Kafka event wrappers and an invalid package path for `NotificationDomainService` (`notification-service/src/test/java/com/example/notification/kafka/FriendRequestEventConsumerTest.java:3-4`, `notification-service/src/test/java/com/example/notification/kafka/MessageCreatedEventConsumerTest.java:7`, `notification-service/src/test/java/com/example/notification/kafka/ReactionEventConsumerTest.java:5`, `notification-service/src/test/java/com/example/notification/application/NotificationKafkaEventApplicationServiceTest.java:7`).

### Low
- `presence-service` carries Kafka dependency and bootstrap configuration (`presence-service/build.gradle:27-45`, `presence-service/src/main/resources/application.yaml:8-12`), but no realtime Kafka producer or consumer implementation was found in main code. That makes the contract surface look broader than the actual delivery path.
- There is a duplicate `common-event-contract` module on disk with its own `EventEnvelope` and `EventMetadata` (`common/common-event-contract/src/main/java/com/example/common/event/EventEnvelope.java`, `common/common-event-contract/src/main/java/com/example/common/event/EventMetadata.java`), but it is not included in `chatappBE/settings.gradle:3-20`. The active services depend on `common-events`, so the duplicate module is currently more of a contract-confusion risk than a runtime owner.

## 5. Risks Before Realtime Edge
- WebSocket ownership is still fragmented across `chat-service`, `presence-service`, `friendship-service`, and `notification-service`, with gateway routes preserving that fragmentation rather than abstracting it away.
- `chat-service` still depends on direct local socket delivery for room membership and moderation events, and still accepts core business commands over WebSocket. A single edge service cannot replace that safely until those responsibilities are externalized behind stable service contracts.
- `presence-service` still mixes presence domain state with connection/session lifecycle, room-subscription memory, and initial snapshot delivery. Moving sockets to edge would otherwise change online/offline semantics.
- Friendship realtime is not fully proven. The producer/consumer payload contract is inconsistent, and the service-local WebSocket publisher is not wired into an actual end-to-end flow.
- Event contracts are not yet stable enough for extraction. The current code violates shared catalog expectations for friendship request events and chat pin/unpin events.
- `notification-service` realtime adapter ownership is not runtime-proven because multiple `NotificationRealtimePort` implementations are active-looking in code.
- Runtime verification is currently weak because the most relevant in-scope chat and notification tests do not compile, so there is no trustworthy automated proof of current end-to-end behavior.

## 6. Readiness Decision
- Not ready yet, needs both ownership cleanup and runtime verification

The codebase is not ready for `realtime-edge-service` yet because realtime ownership is still split across multiple domain services, some important flows still depend on direct in-service socket delivery, and at least two shared contracts are inconsistent with their current producers. On top of that, the test layer that should prove the current behavior is stale enough that chat and notification runtime verification is blocked. In other words, both the ownership boundaries and the proof layer need work before extraction is a safe next step.

## 7. Migration Impact
- Services that would lose WebSocket ownership:
  - `chat-service` would lose `/ws/chat`, `ChatWebSocketHandler`, `ChatSessionRegistry`, `WebSocketRoomBroadcaster`, and `WebSocketUserBroadcaster`.
  - `presence-service` would lose `/ws/presence`, `PresenceWebSocketHandler`, `PresenceSessionRegistry`, and its global/room/user broadcasters.
  - `friendship-service` would lose `/ws/friendship`, `FriendshipWebSocketHandler`, `FriendshipSessionRegistry`, and `FriendshipWebSocketPublisher`.
  - `notification-service` would lose `/ws/notifications`, `NotificationWebSocketHandler`, `NotificationSessionRegistry`, `RedisNotificationSubscriber`, and `WebSocketUserBroadcaster`.
  - `gateway-service` would need to stop proxying four per-service WebSocket routes and proxy a single edge route instead.
- Responsibilities that should stay in domain services:
  - `chat-service`: message persistence, room membership rules, moderation rules, system-message creation, and authoritative chat event publication.
  - `presence-service`: presence state rules, TTL/ephemeral presence state, and authoritative presence state transitions.
  - `friendship-service`: relationship state and authoritative friendship event publication.
  - `notification-service`: notification persistence, unread counts, action-required resolution, and authoritative notification event publication.
- Responsibilities that would need to move to edge:
  - WebSocket endpoints, handshake/session ownership, room/user subscription tracking, and outbound client fanout.
  - Chat and presence inbound WebSocket command handling, or an equivalent edge-to-domain adapter, because those commands are currently processed inside service-local WebSocket handlers (`chat-service/src/main/java/com/example/chat/realtime/websocket/handler/ChatWebSocketHandler.java:96-216`, `presence-service/src/main/java/com/example/presence/websocket/handler/PresenceWebSocketHandler.java:75-118`).
  - Initial snapshot delivery currently emitted directly on connect/join in `presence-service`.
- Contracts or adapters that need stabilization first:
  - Align friendship request topics on one payload type: either actually publish `FriendRequestPayload` for request lifecycle events, or change the shared catalog and all consumers together.
  - Align chat pin/unpin on one shared payload type; the current `MessagePinPayload` vs `RoomMessagePinEventPayload` split is not safe for edge extraction.
  - Externalize chat room membership/moderation delivery into a stable transport path; today those flows still stop at local WebSocket fanout.
  - Decide and prove the single active `NotificationRealtimePort` adapter in `notification-service`.
  - Stabilize the contract source of truth around active `common-events` usage before asking an edge service to depend on it broadly.
  - Restore a working verification path for chat and notification realtime behavior before cutting over client connections.

## 8. Final Recommendation
- The team should not implement `realtime-edge-service` now.
- The team should review and clean current realtime ownership first, then run targeted runtime verification once the stale tests and contract mismatches are fixed.

The strongest next phase is ownership cleanup, not extraction. The current code already has the right idea in some interface comments, but the implemented behavior is still split across service-local sockets, mixed Redis/Kafka fanout paths, and at least one broken friendship contract. Clean that up first, prove the current flows end to end, and only then move client realtime connections behind a single edge.
